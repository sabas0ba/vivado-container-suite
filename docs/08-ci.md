# 08 CI

## 何をテストできるか

Vivado は CI ランナーに入っていないのが普通なので、必要な前提の重さでテストを 3 段に分ける。

| 段 | Vivado | ライセンス | ハードウェア | どこで動くか |
|---|---|---|---|---|
| lint + 単体テスト | 不要 | 不要 | 不要 | 通常のランナー |
| イメージ + 可用性テスト | 不要 | 不要 | 不要 | 通常のランナー |
| フルセルフテスト + 実フロー | 必要 | 必要 | 任意 | セルフホストランナー |

同梱の `.github/workflows/ci.yml` がこの 3 ジョブ構成になっている。

## 単体テスト

```sh
make check      # ピン留め検証 + shellcheck + hadolint + Tcl 構文 + bats
```

bats のテストは偽のコンテナエンジンを `PATH` に置き、`vcs` が組み立てる
コマンドラインをそのまま検証する。マウント構成、ライセンス注入、
ディスプレイ方式、JTAG 方式、権限、エラー時の終了コードが対象。

## 可用性テスト (Vivado なし)

ここが要点で、**Vivado が無くてもコンテナの実体をテストできる**。

```sh
VCS_VIVADO_MODE=none VCS_DISPLAY_MODE=xvfb vcs selftest
```

`VCS_VIVADO_MODE=none` は「このコンテナに Vivado は無い」という宣言で、
ホスト側の Vivado 探索を行わず、Vivado を必要とするステージを skip にする。

| ステージ | Vivado なしで | 内容 |
|---|---|---|
| `image` | 実行 | イメージが存在し、entrypoint が動く |
| `libs` | 実行 | Vivado が dlopen する共有ライブラリ 22 個がすべて解決する |
| `identity` | 実行 | `/work` に作られたファイルが呼び出しユーザ所有になる |
| `display` | 実行 | コンテナ内から X ディスプレイに接続できる |
| `env` | skip | `vivado` / `xsim` / `hw_server` が PATH に載る |
| `version` | skip | `vivado -version` が期待バージョンを返す |
| `tcl` | skip | Tcl スクリプトが完走し `/work` に書ける |
| `license` | skip | ライセンスがコンテナから見える |
| `sim` | skip | 同梱のスモークテストベンチが PASS する |
| `synth` | skip | 同梱のスモーク設計が合成できる |
| `jtag` | skip | `hw_server` に接続してスキャンチェーンを読む |

前提条件が無いステージは**失敗ではなく skip** になる。`mount` / `image` モードで
Vivado が見つからない場合は、意図しない環境不整合なので失敗として扱われる
(`VCS_SELFTEST_REQUIRE_VIVADO=0` で明示的に緩められる)。

`libs` ステージは実用上とくに効く。Vivado は GUI や特定の IP フローに入って
初めてライブラリを dlopen するので、共有ライブラリの欠落は「数十分の合成の
最後で落ちる」形で顕在化しがちだが、このステージは起動直後に検出する。

## セルフホストランナー

Vivado・ライセンス・ケーブルを備えたマシンに `vivado` ラベルを付けて登録し、
リポジトリ変数を設定する。

| 変数 | 例 |
|---|---|
| `VCS_HW_RUNNER` | `true` (このジョブを有効化する) |
| `VCS_LICENSE` | `2100@license.example.com` |
| `VCS_XILINX_ROOT` | `/tools/Xilinx` |

```yaml
runs-on: [self-hosted, vivado]
steps:
  - run: ./bin/vcs build
  - run: ./bin/vcs doctor --deep || true
  - run: ./bin/vcs -C examples/blinky selftest
  - run: ./bin/vcs -C examples/blinky sim
  - run: ./bin/vcs -C examples/blinky flow
```

## 自分のプロジェクトに組み込む

サブモジュールとして取り込んでいる場合:

```yaml
- uses: actions/checkout@<commit-sha>       # v6.0.3
  with:
    submodules: recursive

- name: Build the container image
  run: ./tools/vcs/bin/vcs build

- name: Simulate
  env:
    VCS_LICENSE: ${{ vars.VCS_LICENSE }}
  run: ./tools/vcs/bin/vcs sim

- name: Synthesise and implement
  env:
    VCS_LICENSE: ${{ vars.VCS_LICENSE }}
  run: ./tools/vcs/bin/vcs flow

- uses: actions/upload-artifact@<commit-sha>   # v4.6.2
  if: always()
  with:
    name: reports
    path: |
      build/reports/
      build/logs/
      build/*.bit
```

タイミング未達は `vcs impl` が失敗として扱うので、追加の判定は要らない
(緩めたい場合は `VCS_ALLOW_TIMING_VIOLATION=1`)。

## キャッシュ

`VCS_CACHE_DIR` (既定 `$XDG_CACHE_HOME/vivado-container-suite`) がコンテナの
`$HOME` になる。IP のキャッシュやツール設定がここに残るので、ランナー間で
共有するとビルドが速くなる。

```yaml
- uses: actions/cache@<commit-sha>
  with:
    path: ~/.cache/vivado-container-suite
    key: vcs-cache-${{ runner.os }}-${{ hashFiles('**/*.xci') }}
```

## ピン留めのドリフト検出

`lock-drift` ジョブが `make lock-check` を走らせ、上流のイメージダイジェストや
apt スナップショットとロックファイルの差分を報告する。`continue-on-error: true`
なので、上流が動いただけでプルリクエストが赤くなることはなく、更新は
レビュー可能な差分として扱える。

```sh
make lock          # ロックファイルを更新する (要ネットワーク)
```

## デバッグ

```sh
vcs --dry-run flow      # 実際に走るコンテナコマンドを表示
vcs -v flow             # デバッグログ
vcs info --all --cmd    # 解決済み設定とコマンド全体
```
